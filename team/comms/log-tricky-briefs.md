## Findings (builder bugs, severity order)
B1 HIGH, crashes the whole build to base-agent fallback (I, J, K all hit it). Parser wrote `multi_product.create_promise_failure` as a sentence (string). ecfg.py:383 `(mp['create_promise_failure'] or {}).get('note')` -> AttributeError, generate fails, build degraded, autosim cannot run. Fix: accept str/dict/None in ecfg, flag non-dict in validate.shape_errors, and name the dict shape in the parser prompt. Generic: one malformed optional key must warn, never kill generate. (Sent to coordinator 03:40 UTC.)
B2 HIGH, a product silently vanishes. Per-product amount field (I: overdraft `arrears_nok`, others `amount_due`): the parser emitted `debt_statement.amount_field_by_product` / `amounts.past_due_field_by_product`, the compiler reads only one global `amounts.past_due_field` (or debt_statement.include[0], here `amount_due`). The overdraft is omitted from the statement, the pay-all question and the whole flow (TI-01, TI-08, TI-09, TI-10 fail; the call never mentions the overdraft). Fix: support per-product amount (and days) fields; fall back to the type's own numeric field from the API when the common field is missing; autosim invariant: every product from get_account must be stated and end with a promise or note. The compiler warning list shows it (`debt_statement.amount_field_by_product is not read`), but it is not blocking.
B3 HIGH, floor rounding ignored. I: `amounts.floor_rounding: "round up to a whole krone"` (free text) -> floor 250.10 instead of 251 (TI-05). J: `floor_formula_by_product.card_revolving.round_up_to: 100` -> floor 18430 not 18500 (TJ-01). Fix: structured `rounding` ({"mode":"up","to":1|100}) in the contract and ecfg; accept the spellings seen (floor_rounding text, round_up_to, rounding). Unread rounding keys should be a blocking warning because the amount is wrong.
B4 HIGH (J), reason missing when every outcome needs one. Spec has closing.every_outcome_carries_reason=true and PTP reasons ["RECORDED"], PAID_CLAIMED ["CUSTOMER_STATED"]; engine closes PTP / PAID_CLAIMED with no reason (compile warning "no outcome without reasons: promise outcome taken from the first outcome" is only a note). The record is wrong on every promise call (TJ-01..03, 06, 07, 10, 11, 12). Fix: when the outcome has exactly one allowed reason use it; honour every_outcome_carries_reason; the tool API description also says "Required for every outcome".
B5 HIGH (J), callback day rule. `third_party.callback.allowed_days = "today_or_next_two_working_days"` compiles to `cb_days` but the engine's spoken rule and check stay "today or the next business day": Friday 30 April (2nd working day) is rejected, call closes NO_CALLBACK, booking never made (TJ-04). Autosim also flags it (tp_callback_never_ok). Fix: parse "next N working days" (N from the string/int) in engine_lib.
B6 HIGH (J), calendar-day deadlines unsupported and silent. `bands[].deadline = {"calendar_days_after_today": 10|6, "if_non_business_day": "move back..."}` -> `deadline_bd: None`, no deadline at all: a shared date of 7 May is accepted for a late-band loan whose deadline is 1 May (TJ-07); persuasion dates cannot be capped. cal.warnings empty, build not degraded. Fix: support calendar_days_after_today (+ roll back/forward) in deadline_for; blocking warning whenever a band has no usable deadline.
B7 MEDIUM, renamed parameters / units (K, generator-only). Paths are picked up from the tool API (/v2/identity/check), but request bodies keep the fixed names customer_id/field/answer/product_id/amount/date/time, ISO dates and major-unit amounts; `tool_contract_problems` keys on function names (verify_identity, get_account, ...) so the build is labelled degraded and falls back to base-agent instead of adapting. Real hidden APIs probably keep the seven names (brief H says so), but a unit change (cents) or renamed field would silently send wrong data. Suggest: build request bodies from the API schema property names, convert units from the description (ore/cents, DD-MM-YYYY, HHMM), and at least never fall back to base-agent for a name-only mismatch.
B8 MEDIUM, identity normalisation is prompt-only. For `home_town` ("lower case ASCII: o for ø ...") the pre_process hook does not normalise (Tromsø stays Tromsø); only the LLM tool description says it. Digits-as-words ("zero zero four one seven") also not converted. Date words ARE converted in code. Suggest a deterministic pre-process when the field format says lower case / ASCII / digits only: NFKD + transliteration table (ø->o, å->a, æ->ae, ß->ss, ð->d ...), strip spaces and hyphens, spoken digits -> digits.
B9 LOW, spoken amounts are raw floats from the API ("3000.00", "60000.00", "a revolving card" / "Your a revolving card is ... overdue and 5 days overdue", "Your an auto loan"). Currency, thousands separators, "whole yen only / never say sen" and the product article are ignored. The statement template doubles the article when product_names already contain it.
B10 LOW, amount-ore rule: the first-sentence exact text (`opening.first_sentence_exact`) and `opening.max_confirmation_asks` are listed as unread; fixed engine behaviour is assumed. Check the opening text for brief-specific wording if a judge compares it.
